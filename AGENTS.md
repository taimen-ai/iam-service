# Соглашения для исполнителя iam-service

Этот файл — соглашения репозитория для исполнителя любого вендора (человека или
агента). `CLAUDE.md` ссылается сюда одной строкой. Машиночитаемая часть — соседи,
установка, проверки — в [`.agents/runner.yaml`](.agents/runner.yaml); демон
исполнителя читает её с базовой ревизии задачи, так что её правка на ветке задачи
действует только после вливания.

## Что это за репозиторий

IAM — источник истины идентичности платформы: tenant'ы, principal'ы, внешние
identity, федерация, SCIM, Platform Access Token (PAT) и token exchange с
привязкой к audience. Архитектурные решения — в [`docs/adr/`](docs/adr/) и в ADR
суперпроекта; контракты HTTP и токена описаны в [README](README.md).

## Среда

- Рабочая копия — корень репозитория. Соседи `../platform-auth-sdk` и
  `../control-plane` стоят на ревизиях, закреплённых суперпроектом, и доступны
  **только для чтения**. Правки вне iam-service не делай: сделай свою часть, а
  остальное опиши в отчёте.
- Изменение формата токена или claims — контракт для всех сервисов
  (`platform-auth-sdk` проверяет токены): сверься с ним и закрепи contract-тестом.
- **Контракт другого сервиса не выдумывай** — бери из кода соседа.
- Тесты — на SQLite, отдельной базы и тестовых сервисов нет. Одновременно —
  только один прогон и не в фоне.
- Безопасность выше удобства: новый путь выдачи токена — узкий, короткоживущий,
  с журналом и тестами отказа (конституция, ст. VI).

## Команды

Те же цели зовёт CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) и
проверки исполнителя (`checks` в `.agents/runner.yaml`):

| Цель | Что делает |
|---|---|
| `make install` | `uv sync --frozen` |
| `make lint` | `ruff check` и `ruff format --check` |
| `make fmt` | исправляет то, что ruff умеет исправить сам |
| `make test` | `pytest -q`; аргументы — `make test PYTEST_ARGS="tests/test_people.py -x"` |
| `make migrations-check` | ровно одна голова alembic |
| `make check` | `lint`, `test` и `migrations-check` подряд |

Integration-тесты против живого Keycloak помечены `integration` и без
переменных `IAM_TEST_*` пропускаются; как их запустить —
[`deploy/keycloak/README.md`](deploy/keycloak/README.md).

## Правила

- Архитектурные решения — в ADR: `docs/adr/` сервиса или ADR суперпроекта, как
  принято для затронутой границы. Меняешь контракт API, схему БД или поведение,
  описанное в ADR, — обнови или дополни ADR в том же коммите.
- Номер нового ADR — следующий свободный в `docs/adr/` на `origin/main` на момент
  коммита: параллельные ветки уже занимали один номер.
- Схема БД меняется только миграцией alembic в `migrations/versions/`
  (`NNNN_<slug>`, явные `revision` и `down_revision`); круг
  upgrade → downgrade → upgrade проверяет `tests/test_migrations.py`.
- Документация — на русском; комментарии в коде — как в окружающем коде, имена API
  и сущностей — на английском. README (`README.md` и `README.ru.md`) описывает
  HTTP- и токен-контракты: меняешь публичный API — обнови оба.
- Не коммить секреты, локальные абсолютные пути, `.env`, `.secrets/`, артефакты
  сборки.
- Не трогай `main` и чужие ветки: ветку задачи публикует исполнитель-демон.
- Не делай того, чего нет в задаче. Найденное попутно — в отчёт, а не в код.

## Перед сдачей (обязательно)

Каждый пункт уже стоил круга ревью; сдача без них — возврат задачи.

1. Целевая ветка — `baseBranch` задачи, нет — `main`. Если рабочая копия —
   worktree голого зеркала, простой `git fetch` двигает только `FETCH_HEAD`,
   поэтому:
   `git fetch origin +refs/heads/<baseBranch>:refs/remotes/origin/<baseBranch>`.
   Сливай и сравнивай только с `origin/<baseBranch>`: ушла вперёд — `git merge
   origin/<baseBranch>` и разреши конфликты; проверка —
   `git merge-tree --write-tree origin/<baseBranch> HEAD` без конфликтов.
2. На дереве слияния — полный прогон, как в CI: `make check`. Сборку
   Docker-образа не делай.
3. Одна голова alembic с учётом целевой ветки — входит в `make check`
   (`make migrations-check`).
4. Доработка после отклонения: каждый сценарий из комментария ревью сначала
   воспроизведи тестом, падающим на прошлой попытке, и только потом исправляй.
5. Граничные случаи новой логики — отдельными тестами: пустое, `null`, неверный
   тип, повтор и идемпотентность, параллельные вызовы, пути файловых операций.
6. Безопасность: невидимый или чужой объект — ответ, неотличимый от
   отсутствующего, если так требует ADR; секреты не попадают в журналы и ответы.

В отчёте — перечень проверок по пунктам 1–6: команда и результат.

## Отчёт

Первой строкой — что сделано, одной фразой. Дальше: изменённые места, какие тесты
прогнаны и с каким результатом, что осталось или требует решения человека. Ревью
делает человек, поэтому отчёт должен позволять проверить работу без повторного
исследования.

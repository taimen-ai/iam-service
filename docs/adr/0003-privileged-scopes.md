# ADR-0003 (IAM): привилегированные scope — только члену группы и по явному запросу

*English title: IAM privileged scopes — group members only, on explicit request.*

- Статус: принято (фича runtime-console, задача TASK-000859; найдено
  независимым ревью R004, 2026-09-29; п. 7 дополнен `:enable`, TASK-000907).
- Требования: конституция, ст. VI (узкий путь выдачи, безопасное умолчание).
- Обобщает: п. 3–4 [ADR-0002](0002-iam-people-scope.md) (`iam:people`) — теперь
  это частный случай общего правила. Прецедент: [ADR-0001](0001-iam-agents-scope.md).
- Границы: верхнеуровневые ADR-0012 (Platform Access Token) и ADR-0013 (IAM
  отделён от entitlement и доменной авторизации). Формат access token и его
  claims не меняются.

## Контекст

`federation:exchange` выдавал вошедшему человеку все scope, разрешённые
audience, а при пустом списке scope в запросе — всё сразу. Групповое
ограничение было только у `iam:people` (ADR-0002, группа `people-admins`).
В результате любой федеративный человек tenant'а получал `fleet:admin`, и если
fleet-controller проверяет только scope, этот человек мог выпускать ключи
регистрации узлов fleet. Консоль runtime (R005 и дальше) получает такие токены
для каждого вошедшего.

## Решение

1. **Реестр привилегированных scope** — настройка IAM
   `Settings.privileged_scope_groups()`: scope → ключ группы tenant'а, члену
   которой scope можно выдать. Состав:

   | scope | группа | откуда |
   |---|---|---|
   | `fleet:admin` | `fleet-admins` | встроено (`BUILTIN_PRIVILEGED_SCOPES`) |
   | `iam:people` (`IAM_PEOPLE_SCOPE`) | `people-admins` (`IAM_PEOPLE_ADMIN_GROUP`) | всегда, из настроек ADR-0002 |
   | прочие | по настройке | `IAM_PRIVILEGED_SCOPES` (JSON-объект) |

   Реестр ключуется строкой scope, а не парой audience/scope: scope уже
   несут пространство имён сервиса (`fleet:`, `iam:`), и `fleet:admin`
   привилегирован в любом audience, куда bootstrap его впишет. Настройка
   дополняет встроенные записи и может переназначить им группу, но не снять
   привилегию: безопасное умолчание не зависит от того, не забыло ли
   развёртывание пометить scope. Поэтому реестр — в конфигурации сервиса, а не
   колонкой audience в базе: пометку в базе пришлось бы ставить каждому
   tenant'у bootstrap'ом, и забытая пометка снова раздавала бы `fleet:admin`
   всем.
2. **Группа для `fleet:admin` — отдельная `fleet-admins`**, а не общая
   `platform-admins`: права администратора fleet и администратора людей —
   разные, и одна группа давала бы обе authority сразу (наименьшие
   привилегии). Развёртывание, которому нужна одна группа, может назначить
   её обоим scope (`IAM_PRIVILEGED_SCOPES='{"fleet:admin":"platform-admins"}'`,
   `IAM_PEOPLE_ADMIN_GROUP=platform-admins`).
3. **Выдача в `federation:exchange`.** Привилегированный scope выдаётся, только
   если одновременно:

   - scope есть в allowed scopes audience tenant'а;
   - человек — член активной группы из реестра с `source = local`. Членство —
     любого источника (local, SCIM, federated): проекция групп IdP
     (`groupMappings` провайдера) приводит его к token IdP в той же
     транзакции, до выпуска token;
   - scope запрошен явно. Пустой запрос означает «всё, что разрешено
     audience», **кроме** привилегированных scope — их он не выдаёт никому,
     в том числе членам группы.

   Явный запрос не-члена — `403 scope_not_allowed` целиком (без частичной
   выдачи), с записью `federation.exchange` `outcome = denied` и
   `group:<ключ>` для каждого отказанного scope. Успешная выдача пишет в
   `reason` `privileged:<scope>@group:<ключ>`. `scope_ceiling` token
   не-члена привилегированного scope не содержит.
4. **Группы заводит только bootstrap** (`POST /groups`, `source = local`).
   Federation-проекция группу с ключом из реестра не создаёт (пропускает её,
   пока группы нет), SCIM на создание отвечает `409`, а группа с таким ключом
   иного источника или отключённая прав не даёт. Иначе IdP или SCIM-источник,
   заведя группу `fleet-admins`, раздавали бы `fleet:admin`.
5. **Другие пути выдачи.**

   - *PAT* (`platform-access-tokens:exchange`) привилегированных scope не
     выдаёт никогда, даже члену группы: явный запрос — `403
     scope_not_allowed`, пустой — без них. PAT живёт неделями, а членство
     проверяется при выдаче; authority администратора он не переносит.
     `scope_ceiling` token после обмена PAT — потолок PAT, суженный allowed
     scopes audience без привилегированных: такой scope не попадает и в
     потолок.
   - *Client credentials* service account: `iam:people` не выдаётся никогда
     (ADR-0002). Прочие привилегированные scope — только если bootstrap сам
     вписал их в `scope_ceiling` service account и scope запрошен явно
     (пустой запрос client credentials scope не выдаёт вовсе). Service
     account заводит только bootstrap: это то же явное решение
     администратора, что и членство в группе, и групп для service account не
     вводится.
6. **Где проверяется членство после выдачи.**

   - Там, где IAM сам потребляет scope (`iam:people`), guard перепроверяет
     членство на каждом запросе: выход из группы закрывает путь сразу
     (`403 people_admin_required`, ADR-0002).
   - Для scope чужих audience (`fleet:admin`) членство фиксируется в момент
     выдачи. **Отзыв (выход из группы в IAM или в IdP) действует для уже
     выданного token по истечении его TTL** (`IAM_TOKEN_TTL_SECONDS`, 5 минут
     по умолчанию); следующий `federation:exchange` уже откажет. Сервису,
     которому этого мало, нужна своя проверка на своей стороне — IAM не
     публикует членство в token и не вводит introspection этим решением.
7. **Защита членов групп от онбординг-привязки.** Привязка identity по
   `iam:people` (ADR-0002, п. 6) отказывает `403 people_admin_protected`, если
   цель — член любой группы из реестра любого статуса (`reason` — ключ
   группы). Иначе администратор людей привязал бы свою пару
   `(issuer, subject)` к члену `fleet-admins` без identity и вошёл бы с
   `fleet:admin`. Защита от `:disable` по Bearer (ADR-0002, п. 7) остаётся
   только за группой администраторов людей: отключение не повышает прав.
   Включение (`:enable`, ADR-0002, п. 12) права возвращает, поэтому члена
   любой группы из реестра включает только член той же группы.
8. **Scope без групп — решение зафиксировано.**

   - `control-plane:admin` — только потолок: Control Plane с этим scope лишь
     не сужает права, которые даёт binding Principal в самом Control Plane
     (`narrow_permissions`, `control_plane/infrastructure/auth/iam.py`), и
     ничего к binding не добавляет. Authority администратора — binding в CP,
     а не scope; группы IAM для него не вводятся.
   - `iam:agents` для человека не работает: маршруты агентов принимают только
     `principal_type = service_account` (`403 service_account_required`,
     ADR-0001). Группа ему не нужна.

   Если сервис начнёт давать authority по одному только scope, scope нужно
   внести в реестр (п. 1) — встроенно или через `IAM_PRIVILEGED_SCOPES`.
   **Внесение scope в реестр отнимает его у PAT** (п. 5): уже выпущенные PAT
   с этим scope в потолке перестают его приносить, их владельцам нужен
   federation-вход члена группы или service account.

## Последствия

- Контракт токена не меняется: те же claims, `platform-auth-sdk` отличий не
  видит; contract-тест сверх существующих не нужен. Меняется только, кому и
  при каком запросе IAM выдаёт привилегированный scope.
- Консоль и любой клиент `federation:exchange`, которому нужен `fleet:admin`,
  должны запрашивать его явно; пустой запрос его больше не приносит.
- Развёртыванию (R004, `deploy/bootstrap.py`) нужно отдельной правкой завести
  bootstrap'ом группу `fleet-admins` и наполнить её: владельца — local
  членством либо mapping группы IdP в `groupMappings` провайдера. Без группы
  `fleet:admin` не получит никто — безопасное умолчание.
- PAT локального harness `fleet:admin` больше не приносит; операции fleet из
  CLI — через federation-вход или service account с явным потолком.
- SCIM-группа, чьё имя даёт ключ из реестра (`Fleet Admins` → `fleet-admins`),
  не создаётся (`409`): её нужно переименовать в источнике или связать
  членство через `groupMappings`.

## Отвергнутые варианты

- **Пометка привилегированных scope колонкой audience в базе** — безопасность
  зависела бы от того, пометил ли bootstrap scope в каждом tenant'е; забытая
  пометка молча раздавала бы `fleet:admin`.
- **Общая группа `platform-admins` по умолчанию** — сливает authority
  администратора людей и fleet; остаётся доступной как настройка (п. 2).
- **Проверка членства в IAM на каждом запросе fleet (introspection)** —
  новая зависимость fleet от IAM на горячем пути; короткий TTL token и отказ
  следующего обмена достаточны, а сервис может проверить сам.
- **Привилегированные scope через PAT члену группы** — долгоживущий
  credential переносил бы authority администратора после выхода из группы.
